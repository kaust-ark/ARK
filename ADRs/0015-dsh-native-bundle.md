# ADR-0015: Run an installable Idea2Paper workflow in DSH

Status: Proposed. The November 19 plan below extends the local alpha and the hosted integration.

## Starting point

The Idea2Paper bundle is a local DSH application. Its plugin owns project step transitions and uses the DSH Agent registry for model turns. The hosted application has a separate lifecycle with accounts, quotas, and remote workers. Evaluate a shared workflow after the local bundle demonstrates equivalent recovery behavior.

1. Pin DSH `0.2.1-rc.2`. Install a packed bundle into a fresh profile and prove the CLI can start the application and drive DSH role sessions. Give model stages structured outputs and a bounded number of calls. Keep model and project credentials out of the checkpoint.
2. Run one narrow but complete local workflow. The first experiment compares linear and binary search on deterministic sorted inputs. The plan supplies input sizes and a hypothesis. Measured comparison counts feed the writer and an independent reviewer. A renderer compiles the structured draft to PDF and uses the existing Idea2Paper delivery contract. A rejected draft is checkpointed for inspection.
3. Checkpoint completed stages in an atomic project file. DSH session logs retain individual model turns for inspection. The pinned DSH API reserves its experimental custom session records for in-tree packages, so project state lives in the workspace. Use a single writer lock. Commit experiment output before marking the step complete and reuse that output if a process dies in between. A resumed run starts at the first unfinished step.
4. Install the package tarball in a clean DSH home, use a deterministic loopback model endpoint and check the actual PDF, audit, stage artifacts, and DSH request trace. Interrupt after the experiment and before draft completion, then resume. Check that completed model stages and experiment output are reused. Exercise a rejected review and a provider error.
5. Before public distribution, run a bounded real-model pilot with an approved provider, test clean dependency installation and document supported platforms, model configuration, and recovery. Distribute the built npm bundle and optionally add an entry to a Discover index. Treat Slurm as a separate follow-up with scheduler-backed job identity, an idempotent submission protocol, and cancellation and resume tests on real short jobs. Verify hosted parity before adopting the bundle there.

The next local milestone accepts a general idea within a CPU-only experiment budget. DSH plans the experiment and generates Python code as structured data. The host runs that code in a pinned container with no network or host mounts. Persist the project ID and script before container creation. On resume, reconcile the named container before trying to create one. Persist experiment results before removing the container. An independent reviewer checks the method, code, results, and draft. Allow one revision and a fresh review. Compile and audit in a staging directory before exposing the final PDF.

The hosted integration runs a dedicated Cordis plugin from the same pinned runtime wheel as the agents. The plugin advances the production research, experiment, and review phases through a private inherited socket. The worker executes the existing Python steps and writes the same project checkpoints and artifacts. The hosted plugin receives stage outcomes through that socket. Model credentials stay in the worker and its existing agent processes. Webapp launches with a project ID select the plugin by default. Set `ARK_WORKFLOW_RUNTIME=python` in the launching environment to use the previous workflow with the same DSH agents and checkpoints. `ARK_AGENT_RUNTIME=cli` still opts into the OpenHands path.

### What the bundle owns

1. **Project session.** On project creation, allocate an owner session ID and durably claim it under the existing project lock before the first billed turn. Use the DSH agent registry to create or resume that ID with the same workspace, compatible runtime and model configuration. Keep DSH session storage across worker restarts. The owner carries the research question through investigation, coding, writing and revision. Store current decisions, frozen controls, outstanding evidence and artifact paths in the existing project state so context compaction and operator recovery have a reliable reference. [DSH agent registry](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/core/agent/README.md)
2. **Research workflow.** The bundle registers project tools and the rules for when work can advance. For a fresh project requesting Google Deep Research, start or recover the recorded interaction before experiment planning. Return its report and sources to the owner. The owner may revisit research, reanalyze observations or request another experiment within budget. Persist the reason for each decision. Phase names are progress labels and prerequisites. Switching phase preserves the owner session and its system identity. Use a deterministic workflow for operations such as submit/reconcile or compile/check. Keep the native agent loop responsible for choosing tools and responding to results. [Existing decision contract](0016-research-evidence.md) · [DSH tools](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/core/tools/README.md)
3. **Skills and tools.** Load all six shipped built-ins from the installed distribution at project initialization, including resumed writing-only projects. Select domain skills from the existing catalog after the topic is known. Convert role prompts into a stable owner brief, task-specific instructions and one reviewer preset. Map only operations with a scientific or operational meaning to tools, such as obtaining research evidence, running or reconnecting an experiment, compiling the paper and requesting review. Reuse the Python implementations behind those tools, including LaTeX, citation resolution, figure generation and Slurm. Avoid a tool per old internal phase or separate coding/writing agents. [Built-ins](../skills/builtin) · [Skill catalog](../skills/index.json) · [DSH skill loader](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/skill/skill-filesystem/README.md)
4. **Independent review and delivery.** Give the owner a bounded review tool backed by native `spawn`. The reviewer gets a fresh conversation, a read-only artifact snapshot, the relevant rubric and no delegation, shell or write access. Record its verdict against manuscript, figures and evidence revisions. Material edits invalidate the prior verdict. Reuse the record on retry and honor the existing review limits. The delivery operation verifies the current artifacts and matching review before recording completion. Separate scientific judgments, hard contract failures and advisory warnings. A normal end of the owner's turn can update progress or prompt for missing evidence. Cancellation, timeout and provider failure also end turns and must preserve their real outcomes. [Native spawn](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/subagent/subagent-spawn-in-process/README.md) · [Delivery contract](../ark/delivery_contract.py)

### The project as the user sees it

The project page should answer three questions on first glance. What just changed in the research? What evidence can I open? Does the researcher need me to decide something? Give the current scientific action and latest confirmed observation the most space. Keep a compact phase timeline above them. Let the user open the corresponding paper page, plot, primary-source passage or experimental result next to the conversation. Show the researcher’s decisions and observed tool outcomes. Raw tool logs belong in an expandable diagnostic view with the existing access controls.

| Moment | Visible behavior and action |
|---|---|
| A plan needs approval | Keep the question, alternatives, consequences and existing timeout/default together. Let the user approve or change the plan in place. Show the command as queued, then acknowledged or failed. Preserve their draft and decision ID through a reconnect. |
| An experiment or research request is running | Advance on confirmed events, such as a search report arriving or three of five splits returning. Use a count only when the denominator exists. For an opaque provider request, show the last observation and elapsed time. Distinguish queued, running, waiting for the user, stopped, quota-paused and disconnected. Let the owner ask a status question, steer the next action or Stop. |
| An independent review needs a repair | Show the specific claim, page/figure and supporting observation. For a misplaced figure arrow, open the actual image at the criticized revision. After repair, toggle between the two rendered versions at the same location. Keep the issue open until the matching revision is checked. A user may ask why, supply evidence or choose to narrow the claim. |
| Work resumes or a paper is delivered | Return to the last acknowledged action and existing job. Preserve the history, including failed attempts. On delivery show the current PDF and its own audit. Later edits mark that revision as awaiting review. Enforce the current owner/shared-view permissions on evidence, diagnostics and actions. |

**Motion and access.** Move the phase marker once when the recorded milestone changes. Reveal a newly published artifact in place, and keep the reader’s selected page and scroll position during a revision comparison. Use short transitions around 180–300 ms. Freeze the indicator when work is waiting or disconnected. Honor reduced motion, keyboard navigation, focus return, touch targets and explicit text statuses. Announce submitted decisions and milestone changes to assistive technology. Suppress token-level announcements. Keep equivalent progress, evidence paths and decision prompts in the CLI, with a line-oriented mode for redirected output. Use DSH Web's existing question, subagent and deliverable views where available.

**State and implementation.** Extend the existing project event stream and dashboard panels. Persist confirmed changes with a project cursor and deduplicate native events by session ID and sequence, and external results by durable job/interaction identity. Keep live tokens and heartbeats transient. Serve an authorized snapshot with its cursor, then replay subsequent events on reconnect. The current SSE stream has per-connection cursors and separate log, message and status paths. Test loss of connection between the snapshot and the first event, duplicate events, and browser refresh during a pending decision. A reconnect must neither replay the animation history nor submit the decision twice. ### A reviewer that earns its verdict

The community alpha sees structured text and returns acceptance, unsupported claims and feedback. The hosted reviewer already reads venue instructions and checks source references, experiments and rendered pages where its model supports vision. It also passes the previous score into subsequent rounds and has a score-based acceptance threshold. An earlier text-only review assigned presentation 8/10 without seeing the pages. Preserve the useful scientific rubric and make individual judgments and their evidence inspectable. Track paper format and target track independently. A four-page ICML-format exercise gives evidence about a four-page paper, not main-track acceptance. [Alpha review](../integrations/dsh/workflow.js) · [Hosted rubric](../ark/templates/agents/reviewer.prompt) · [Score parsing](../ark/orchestrator/core.py)

1. **Review the submission blind.** Give one native reviewer a read-only snapshot of the specified submission and venue rubric. It first identifies the central contribution, the strongest supporting observation, the strongest competing interpretation, missing controls or baselines and the scope of each headline claim. Reserve the author's conversation, prior scores and unpublished output until this reading is complete.
2. **Verify the consequential claims.** Let that same reviewer request named, read-only evidence operations for a cited original, a recorded experimental comparison, a deterministic recomputation, or a rendered PDF page and crop. Distinguish what a venue reader can establish from the submission and what a separate reproducibility check verified from worker artifacts. A correct figure in the raw files does not fix a mislabeled figure in the paper. Record missing sources, disabled vision and unavailable measurements as unassessed. Use a visual-capable check when visual correctness is required for delivery.
3. **Make findings actionable.** Each material concern names the disputed text or figure, exact location, observed evidence, why it matters, severity and the smallest change or observation that would resolve it. A supported negative result is a valid outcome. Permit a narrower conclusion when it answers the brief. Include strengths and uncertainties. Distinguish a scientific blocker, an unresolved question and optional polish. Validate evidence references and revision identity in code. Keep a score optional for display and reject malformed scores. A score alone cannot clear a blocking finding.
4. **Verify the revision.** Lock the initial finding set to that snapshot. Give the reviewer the item IDs, evidence and revised passages for a second pass. Track resolved, still present, newly introduced and unassessed findings. Check material changes elsewhere in the manuscript as well. Use the existing revision and spending budgets. If the same blocker survives the budget, return the draft and evidence to the owner with an explicit outcome.

**Prove review quality before making it a delivery dependency.** Compare the current reviewer and candidate on the same model, materials and tool-call budget. Blind variant labels and previous scores. Freeze paired flawed and corrected artifacts from the digits study (maximum of split means described as an individual maximum, or a temperature fitted on the wrong branch), Friedman (misattributed primary source or an unsupported causal explanation) and an unseen study. Include sound negative results and unverifiable statements to test false alarms and abstention. The manuscript acceptance script checks artifacts on two known cases. Evaluate reviewer judgment separately, with a knowledgeable reader adjudicating disputed findings against the sources. A recent preprint uses planted errors and clean controls for precisely this distinction. [Manuscript checks](../scripts/eval_manuscript.py) · [Auditing AI peer reviewers](https://arxiv.org/abs/2611.17052)

For each pair report confirmed major defects found / present, unsupported blocking findings on clean controls, correct evidence locations, and whether the reviewer clears the corrected issue without accepting a sham fix. Report quality of the scientific reasoning separately from deterministic typography or arithmetic checks. Record requests, elapsed time and spend, and show the numerator and denominator for small samples. For the initial release fixture, require detection of every predeclared critical control/claim swap, zero false delivery blocks on its clean twin, correct revision identity and explicit abstention when the required evidence was withheld. Hold out one topic for the final comparison. Publish only redistributable fixture excerpts and redacted examples. Label these release gates as test targets until the blind comparison has run.

### Hosted execution of the pinned Python companion

The dashboard launches local and Slurm workers through the same Python module entry point. Each native worker selects the archive recorded for its project and verifies the installed JS files against that archive. A fresh interpreter loads the wheel's first-party research code and assets from a temporary directory. The project's existing conda environment still supplies site dependencies, and the separately configured DSH interpreter starts the agent runtime. The scheduler continues to track the same process ID. The worker log records both the archive and wheel SHA-256.

The service keeps previously selected archives in its cache outside project workspaces. A rollout selects the new archive for new projects and retains the earlier archive for existing sessions. For installations predating this cache, retain the original release tarball or its source-build cache when moving workers to a different host. If neither contains the recorded digest, restore that release tarball before resuming. Legacy checkpoints use their existing runner.

An isolated upgrade from v0.5.48 reproduced a failure before the first legacy stage checkpoint. A project that had passed Gate A acquired a second owner on Continue. ### Product acceptance for progress and review

Start the community walkthrough in the middle of a working project. Let the reader follow one real sequence from a measurement to the manuscript page, the reviewer's independent check and the author's revision. Each event carries a human-readable observation. The website shows a short arrival transition once for a new observation, keeps the selected phase usable during incoming updates and opens the corresponding artifact in context. An archived review opens its frozen PDF. A mutable project file is labeled as the current version. The CLI presents the same event text and artifact location. Persisted event IDs should support a replay with the same order after disconnection. For work with an unknown denominator, show its last confirmed action and time. A numeric progress bar requires a known count. Respect the system reduced-motion preference throughout. [W3C animation guidance](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)

Use this walkthrough as a product test. A first-time reader on desktop and on a narrow phone must be able to locate the disputed page and the measurement, tell whether the finding is provisional or signed off, and return to the event they selected. A project owner can steer, stop or respond to a pending decision there. A shared viewer sees only authorized artifacts and actions. Test a new event arriving while inspecting an artifact, a reconnect during plan approval and a stale review after a manuscript edit.

Keep scientific judgment in the independent DSH reviewer. Ask which observation supports the main contribution, which alternative could explain it and which check would distinguish the two. Include original-source attribution, scientific correctness and significance in the review reasoning. Ask for the smallest feasible follow-up when the available evidence is insufficient. Host checks validate provenance, deterministic facts and verdict completeness. A reviewer may amend its own rejected draft during the same activation. A changed experiment, figure or manuscript requires review of the new revision. [NeurIPS reviewer guidelines](https://neurips.cc/Conferences/2025/ReviewerGuidelines)

#### Following an observation through review

The unit of interaction is a recorded observation. A person returning to a project can open one recent result, see the decision it affected and challenge that decision in the owner's existing conversation. Use the same event identity for the progress overview and its entry in history. Keep the last three meaningful observations in reach. Animate the newest arrival once per update. On reconnect, restore the reader's place and their unsent question. Reduced-motion users get the same text and actions immediately. Test the path on a phone with touch and on desktop with a keyboard, including an update while the reader is inspecting an older result. The native bundle supplies the observation, revision and artifact reference. The host supplies navigation, animation and permissions.

The scientific acceptance case follows the same path. In the Friedman example, five paired error measurements support a performance difference. Identifying the dominant mechanism requires a distinguishing measurement. The original reviewer accepted it. The reader subsequently obtained a qualified conclusion while the original assertion survived in the discussion. Turn this into a revision test across multiple PDF pages. If an open finding locates the same assertion in several passages, closing it requires repairing those locations or presenting new supporting evidence. Keep an unrelated methods passage as a control for overblocking. Give the reader a link to the actual passage and measurement for each disputed finding.

Before making this the hosted default, compare the candidate with the released reviewer on the same frozen manuscripts, model, request limit and cost ceiling. Include a flawed original, a partial repair, a defensible paper with a null result and a paper with its raw evidence withheld. Score correctly located major issues, false blocks, justified abstentions and how often a signed verdict is produced within budget. A capped run counts as unfinished. Use a second subject that has not informed the implementation, withhold adjudication from the reviewer, and report every run and its cost. The public replay lets people inspect the evidence without model credentials.

The full-paper trial exposed a more specific design problem. A single assessment currently covers an entire passage. The reviewer justified the observed increase in RMSE, and the same signature covered a stronger sentence about the cause. A generic counterexample prompt left that signature intact. For the next change, use the existing manuscript check and archived findings to record separate decisions about the result and its explanation. Each decision should point to an exact author sentence. For a claim of mechanism, show the discriminating observation the reviewer asked for before reading and the supporting measurement or derivation it actually found. Allow a qualified hypothesis to remain. A missing test should yield a located revision request when the author presents the mechanism as established. Surface these distinctions in the current review card so the owner can discuss either passage. Evaluate this change on clean, flawed and partially repaired full papers before promoting it. The next change belongs in experimental design as well as review. When the research question asks why a result occurs, use the existing plan approval to show the two explanations, a measurement that gives different predictions under them, and which conclusion remains possible without that measurement. A descriptive comparison can go ahead on its own terms. In review, follow the calculation to the quantity named in the sentence. Try to construct two cases with the same cited evidence but different answers to that question. A valid counterexample should lead to a revision request at the disputed sentence.
